#I. Server Deployment Architecture

The entire architecture adopts a seven-layer hierarchical design, from outside to inside as follows:

Layer Core Responsibilities Key Technologies
Access Layer Traffic entry, security protection, static resource acceleration CDN + WAF + SLB
Gateway Layer Reverse proxy, rate limiting, routing distribution Nginx (multi-active deployment)
Application Layer Business logic processing PHP8-FPM stateless cluster
Cache Layer Hot data caching, Session storage, distributed locks Redis Cluster
Database Layer Persistent storage, read-write separation PolarDB MySQL
Storage Layer File/object storage, image processing Alibaba Cloud OSS
Operations Layer Log collection, monitoring & alerting, configuration management SLS + Cloud Monitor

Core Design Principles:

  • Stateless Application Layer: All API Servers store no state; Sessions are centrally stored in Redis, supporting horizontal elastic scaling
  • Read-Write Separation: Database writes go to the primary instance, reads to read-only instances; PolarDB provides automatic read-write separation + consistency level control
  • Cache Penetration Protection: Redis Cluster deployed at the front for hot data caching, combined with Bloom Filter to prevent cache penetration (Note: Bloom Filter is mainly used to prevent cache breakdown; empty value caching is commonly used for cache penetration prevention)
  • CDN Traffic Offloading: All static resources (JS/CSS/image thumbnails) are hit by CDN, significantly reducing origin server pressure

#II. Functionality & Cloud Service Support

Function Module Specific Service Function Description
Computing ECS Elastic Compute Service Compute-optimized instances with high network bandwidth
Load Balancing SLB (ALB) Application Load Balancer supporting HTTP/HTTPS Layer 7 forwarding, WebSocket and gRPC protocols
Static Acceleration CDN (DCDN Full-site Acceleration) Accelerates both static resources and dynamic APIs, improving access speed via edge node near-user response
Web Security WAF 3.0 Provides protection against common Web threats such as SQL injection, XSS, CC attacks
Database PolarDB MySQL 100% MySQL compatible, up to 1 million QPS, supports automatic read-write separation
Caching Redis (Cluster Edition) Hybrid memory and SSD storage, balancing high performance and data persistence with high-availability architecture
Object Storage OSS Supports tiered storage strategies (Standard, Infrequent Access, Archive) to effectively reduce cold data storage costs
Image Processing OSS Image Processing (IMG) Implements thumbnails, watermarks, and format conversion using built-in OSS capabilities without additional computing resources
Log Service SLS Log Service Centralizes management of all server logs, supporting real-time collection, analysis, and alerting
Monitoring & Alerting Cloud Monitor + ARMS Full-link monitoring covering infrastructure and application layers for real-time early warning
Message Queue RocketMQ Used for asynchronous task processing, implementing peak shaving/valley filling and system decoupling for time-consuming operations
Container Orchestration ACK Smooth migration to Kubernetes containerized deployment as server scale expands in the future

#III. Resource Strategy & Architectural Approach

#3.1 Concurrency vs. Resource Relationship

Baseline Application Server: 8-core 16G ≈ 400 QPS/node
Peak QPS Calculation:
  Total Daily Requests = 7 million DAU × 50 times/user = 350 million
  Requests in Peak Window (4h) = 350 million × 80% = 280 million
  Peak QPS = 280 million / (4×3600) ≈ 19,445 ≈ 20,000

Number of API Servers: 20,000 / 400 ≈ 50 nodes

#3.2 Database Capacity Planning

PolarDB MySQL is adopted with built-in read-write separation (this QPS is based on the current cloud disk scenario with large SQL queries, lower than the benchmarked QPS)

Standard Instance: 16-core 32G + 100GB SSD
Peak SQL QPS = 20,000 × 20 = 400,000 QPS (Read: 320,000 / Write: 80,000)
PolarDB Read-Only Instance ≈ 20,000 QPS; Read-Write Instance ≈ 10,000 QPS
  Required Read-Only Instances: 320,000 / 20,000 ≈ 16 nodes
  Required Read-Write Instances: 80,000 / 10,000 ≈ 8 nodes

#3.3 Redis Capacity Planning

Session Storage: 7 million DAU × 5KB ≈ 35GB
Other Cache Acceleration: 7 million DAU × 10KB ≈ 70GB

Configuration: 4 nodes, 8 vCPU / 32GB memory per node
Combined with LRU eviction policy + TTL expiration

Strategy Implementation Method Benefits
Statelessness Sessions, caching, etc. centrally stored in Redis; no local state on API Servers Arbitrary scaling, automatic failure removal
Read-Write Separation PolarDB automatic read-write separation + linear scaling of read-only instances Horizontal scaling of read capacity; write bottlenecks resolved via instance upgrade
Multi-level Caching CDN (Edge) → Redis (Cluster) → DB, with Bloom Filter for anti-penetration Gradually reduce backend pressure, 99% of requests hit cache
Asynchronous Decoupling Large file upload/transcoding/virus scanning → RocketMQ → Asynchronous Worker Avoid long connections occupying API resources
Hot/Cold Tiering OSS Standard→Infrequent Access→Archive, automatic sinking based on access frequency Reduced storage costs

#Others

Notes

  1. Storage and bandwidth are not considered in the above architecture (object storage is used; uploads/downloads are directly transmitted without passing through the application layer)
  2. Subsequent development will focus on SQL optimization (reducing the number of SQL queries per API call, which can reduce database scale; adding thread pools can improve concurrency)
  3. Gray-scale launch, dynamically adjust resource configuration based on actual DAU and QPS data
  4. PolarDB natively supports automatic read-write separation without additional middleware
  5. Cost estimation order: Storage Cost > Traffic Cost > Database > Application Servers > Others
